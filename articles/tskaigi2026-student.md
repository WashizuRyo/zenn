## tscからtsgoへ ── DenoのTypeScript基盤はどう変わったか

Day1 で最初に印象に残ったのは、`deno check` についてのセッションです。

https://2026.tskaigi.org/talks/2

Deno には、TypeScript がそのままでは理解できない Deno 固有の API や specifier があります。そのため、`deno check` では Deno の世界のコードを TypeScript 側でも解釈できるように変換する必要があります。

もともとは `deno run` で実行と型チェックを行っていたものが、2025年から `deno check` として分離され、`deno run` は実行に集中する形になったそうです。セッションでは、その裏側でどのように TypeScript のチェックを成立させているのかが、段階ごとに説明されていました。

特に面白かったのは、`typescript-go` への移行の話です。最初は Deno 固有の概念を扱うために `denoland/typescript-go` を使っていたものの、LSP 対応や fork のメンテナンスコストが大きくなり、最終的には `microsoft/typescript-go` を使う方向に進んだという話がありました。`deno check` が約2.6倍高速化したという性能面だけでなく、長期的にメンテナンスできる形に寄せていく判断が印象的でした。

## 業務に残された「よくない型」で考える「TypeScriptの難しさ」

https://2026.tskaigi.org/talks/5

「プロダクトの良くない型」についてのセッションでは、自分のコードでも心当たりがある話が多くありました。

入力値、クリックハンドラ、`try catch` の `error` など、動的な境界では型が広くなりがちです。そこで安易に `as` を使ってしまうと、型を狭めているつもりでも、実際には危険な仮定をコードに埋め込んでしまうことがあります。`const value = config as Record<string, unknown>` のようなコードも、一見安全そうに見えて、以降の処理では広すぎる型を扱うことになります。

このような場面では、型ガードを使って実行時に値を確かめながら型を狭めることが重要だと感じました。また、`Array.filter`、`includes`、`Array.isArray` など、標準メソッドだけでは推論が思ったように効かないケースも紹介されていました。ヘルパー関数や型ガードを用意することで、`as` に頼らずに型安全に扱えるようにするという考え方は、自分のコードでも見直したいポイントです。

## OSSのコードベースにneverthrowを漸進的に導入して、AIにも人間にも優しいエラーハンドリングを実現する

https://2026.tskaigi.org/talks/11

エラーハンドリングのセッションでは、関数の戻り値を `Result` 型にすることで、シグネチャを見ただけで失敗しうる処理だと分かるようにする話がありました。例外が投げられるかどうかが実装を読まないと分からない状態よりも、戻り値の型に失敗の可能性が現れている方が、呼び出し側にとって親切です。

## TypeScriptのclassはなぜこうなったのか — 歴史・落とし穴・そして使いどころを探る

https://2026.tskaigi.org/talks/16

TypeScript の class についてのセッションでは、`User` クラスを受け取る関数に `Product` を渡しても、条件によってはトランスパイルや実行が通ってしまうという話がありました。

TypeScript の class は ECMAScript 2015 よりも前に実装されており、その後 ECMAScript 側の class と整合を取っていく必要がありました。TypeScript は JavaScript の上にある言語なので、JavaScript の仕様や歴史と切り離して考えることはできません。普段何気なく使っている `class` にも、言語仕様としての積み重ねや難しさがあることを知れたのが面白かったです。

## TS 7: How We Got There

https://2026.tskaigi.org/talks/37

`tsgo` の実装についてのセッションでは、TypeScript コンパイラが Go で書き直される話について、背景や実装の流れを知ることができました。自分はそれまで「TypeScript のコンパイラが Go になるらしい」くらいの理解でしたが、なぜその取り組みが必要なのか、今後 TypeScript の開発体験にどう影響しそうなのかを考えるきっかけになりました。

# Day2

Day2 も、TypeScript をプロダクトや設計にどう活かすかという話が多く、Day1 とはまた違った学びがありました。

## 400超のデータポイントを型で制す —— UPSIDERの与信審査エンジンを支えるTypeScriptの「柔軟性」と「結合力」

https://2026.tskaigi.org/talks/39

審査を毎日行うようなプロダクトで、バックエンドの技術選定として Java、Go、TypeScript を比較し、最終的に TypeScript を採用したという話がありました。TypeScript は静的型付け言語としての堅さがありつつ、JavaScript 由来の柔らかさも持っているという点が選定理由として語られていました。

400以上の特徴量を扱うために Zod schema でフラットに管理し、境界では `z.parse` や `z.partial` を使うという話も印象的でした。型定義をただ書くだけでなく、実行時の値検証と合わせて使うことで、プロダクトの複雑さを扱いやすくしているのだと感じました。

AI を使った開発フローの話もありました。PRD を作り、設計レビューは人間が行い、その後の実装を AI に任せ、最後にテストで確認するという流れです。AI に任せる部分と人間が責任を持つ部分を分けることが、今後の開発では重要になりそうだと感じました。

## React の props は値の集合ではない — UI の状態を宣言するコンポーネント設計

https://2026.tskaigi.org/talks/41

React コンポーネントの props に `data`、`isLoading`、`error` が並んでいると、本来ありえない状態を表現できてしまいます。たとえば、`isLoading` が true なのに `data` も存在する、`error` と `data` が同時に存在する、といった状態です。

この問題に対して、discriminated union を使うことで、状態ごとに許される props を型で表現できるという話がありました。状態を boolean の組み合わせとして持つのではなく、「loading」「success」「error」のような意味のあるまとまりとして表現することで、コンポーネントの利用側も実装側も安全になります。

一方で、`refetching` や `refetchingError` など状態が増えていくと、単純な union だけでは扱いにくくなります。TanStack Query の `useSuspenseQuery` のように、loading や error を上位のコンポーネントで処理する設計が参考になるという話は、型だけでなくコンポーネントの責務分割としても学びがありました。

## Auth.jsからBetter Authへの移行に見る「型とランタイム」の設計思想の変化

https://2026.tskaigi.org/talks/43

認証ライブラリのセッションでは、NextAuth から Auth.js、Better Auth への流れが紹介されていました。Auth.js では session の型をユーザー側で拡張できますが、callback で実際に値を渡していなくても型推論上は存在するように見えてしまう問題があります。一方で Better Auth は、auth インスタンスの config を元に型を推論することで、実装と型のずれを減らしているという話でした。

ライブラリの型設計は、単に型が詳しいだけでは不十分で、実際の設定や実行時の挙動とずれないことが重要なのだと感じました。

## Node.js+TypeScriptにおけるCJS/ESM相互運用の最新ポイント

https://2026.tskaigi.org/talks/56

CommonJS と ES Modules の違いについてのセッションでは、`import` / `export` の違いや top-level await など、普段なんとなく使っているモジュールシステムの背景を整理できました。

## enum よ、さようなら

https://2026.tskaigi.org/talks/57

enum についてのセッションでは、`enum` が TypeScript 独自の構文であることを改めて意識しました。TypeScript は JavaScript に型を足す言語ですが、`enum` のように実行時のコードにも影響する独自機能があります。便利さだけでなく、JavaScript との距離感を考えて使う必要があると感じました。

## いつテストを書くか？―ソフトウェア開発における安心と不安について考える

https://2026.tskaigi.org/talks/63

Day2 で特に心に残ったのは、変更容易性と TDD の話です。

保守性とは変更容易性であり、ソフトウェアの「ソフト」は簡単に変更できることを意味する、という話から始まりました。変更が困難になったソフトウェアは、もはやソフトではなくハード化しているという表現が印象的でした。

変更容易性には、変更できそうだと思える「予期的変更容易性」と、実際に変更している中で感じる「経験的変更容易性」があるという整理も分かりやすかったです。自分がコードを読むときに「ここは触れそう」「ここは怖い」と感じるのは、単なる気分ではなく、システム理解やテスト、設計の状態に支えられた感覚なのだと思いました。

開放閉鎖原則についても、既存の要求を満たす振る舞いが変わらないことが「閉じている」、新しい振る舞いを追加できることが「開いている」と説明されていました。そして、TDD は開放閉鎖原則を徐々に閉じていく行為だという話がありました。

テストは既存の要求と期待される振る舞いの定義であり、変更しても既存テストが壊れないなら閉じていると言えます。一方で、新しい機能のテストを書くのが大変なら、設計が開いていない可能性があります。Red、Green、Refactor の最後にリファクタリングがある理由は、実装を通じて得た学習をもとに、開放閉鎖を回復させるためだという説明がとても腑に落ちました。

「いつテストを書くべきか」という問いに対して、触るのが不安ならそれがテストを書くタイミングだ、という話も印象的でした。E2E/UI テストは不安の解消、ユニットテストは構造フィードバックという整理は、これから自分がテストを書くときの判断軸にしたいです。

# おわりに

TSKaigi 2026 は、TypeScript の最新動向を知るだけでなく、型を通してプロダクトや設計、チーム開発を考えるきっかけになるイベントでした。

学生支援制度があったからこそ、現地でセッションを聞き、スカラシップランチや懇親会で人と話し、普段の学習だけでは得られない視点を持ち帰ることができました。改めて、学生支援企業の皆様、運営の皆様、登壇者の皆様に感謝します。

今回学んだことを、自分の開発や学習に少しずつ取り入れていきます。特に、型をただ書くのではなく、実行時の振る舞いや変更しやすさと結びつけて考えることを意識していきたいです。
