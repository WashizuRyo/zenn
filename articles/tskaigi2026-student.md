# はじめに

TSKaigi 2026には、学生支援制度を利用して参加しました。

まず、このような機会を支えてくださった学生支援企業の皆様に感謝します。ソフトバンク株式会社、株式会社アイスタイル、株式会社アサイン、株式会社SmartHR、株式会社ドワンゴ、株式会社プレイド、株式会社LayerX、レバレジーズ株式会社のご支援により、学生である自分も現地でイベントに参加し、セッションやハンズオン、OST、懇親会を通じて多くの学びを得ることができました。

# 事前イベント

事前イベントでは、各スポンサー企業の会社説明に加えて、スポンサー企業の方と直接話せる時間がありました。前半は各社の会社説明、後半は1社につき学生が5人ほどのグループに分かれて話す形式でした。

自分は株式会社アイスタイルさんとソフトバンク株式会社さんの担当者の方とお話しすることができました。時間はあまり長くなかったため深いところまでは聞けませんでしたが、各社でTypeScriptをどのように使っているのかや、AI活用について話すことができました。

# Day1

Day1のオープニングトークでは、TSKaigiがTypeScriptのイベントとして世界規模で見ても大きな存在になっていることや、TypeScriptを取り巻く環境が大きく変化していることが語られていました。TypeScriptコンパイラがGoで書き直されていること、DenoやBunなどのエコシステムが進化していることなど、TypeScriptは言語そのものだけでなく周辺環境も含めて動き続けているのだと感じました。

## tscからtsgoへ ── DenoのTypeScript基盤はどう変わったか

https://2026.tskaigi.org/talks/2

Denoには、TypeScriptがそのままでは理解できないDeno固有のAPIやspecifierがあります。そのため、`deno check`ではDenoの世界のコードをTypeScript側でも解釈できるように変換する必要があります。

もともとは`deno run`で実行と型チェックを行っていたものが、2025年から`deno check`として分離され、`deno run`は実行に集中する形になったそうです。セッションでは、その裏側でどのようにTypeScriptのチェックを成立させているのかが、段階ごとに説明されていました。

特に面白かったのは、`typescript-go`への移行の話です。最初はDeno固有の概念を扱うために`denoland/typescript-go`を使っていたものの、LSP対応やforkのメンテナンスコストが大きくなり、最終的には`microsoft/typescript-go`を使う方向に進んだという話がありました。`deno check`が約2.6倍高速化したという性能面だけでなく、長期的にメンテナンスできる形に寄せていく判断が印象的でした。

## 業務に残された「よくない型」で考える「TypeScriptの難しさ」

https://2026.tskaigi.org/talks/5

「プロダクトの良くない型」についてのセッションでは、自分のコードでも心当たりがある話が多くありました。

入力値、クリックハンドラ、`try catch`の`error`など、動的な境界では型が広くなりがちです。そこで安易に`as`を使ってしまうと、型を狭めているつもりでも、実際には危険な仮定をコードに埋め込んでしまうことがあります。

このような場面では、型ガードを使って実行時に値を確かめながら型を狭めることが重要だと感じました。また、`Array.filter`、`includes`、`Array.isArray`など、標準メソッドだけでは推論が思ったように効かないケースも紹介されていました。ヘルパー関数や型ガードを用意することで、`as`に頼らずに型安全に扱えるようにするという考え方は、自分のコードでも見直したいポイントです。

## OSSのコードベースにneverthrowを漸進的に導入して、AIにも人間にも優しいエラーハンドリングを実現する

https://2026.tskaigi.org/talks/11

このセッションでは、関数の戻り値を`Result`型にすることで、シグネチャを見ただけで失敗しうる処理だと分かるようにする話がありました。例外が投げられるかどうかが実装を読まないと分からない状態よりも、戻り値の型に失敗の可能性が現れている方が、呼び出し側にとって親切だと感じました。Rustのように`Result`型が標準的に使われている言語にも触れて、エラーを値として扱う設計の感覚をもう少し掴みたいと思いました。

## TypeScriptのclassはなぜこうなったのか — 歴史・落とし穴・そして使いどころを探る

https://2026.tskaigi.org/talks/16

TypeScriptのclassについてのセッションでは、`User`クラスを受け取る関数に`Product`を渡しても、条件によってはトランスパイルや実行が通ってしまうという話がありました。

TypeScriptのclassはECMAScript 2015よりも前に実装されており、その後ECMAScript側のclassと整合を取っていく必要がありました。TypeScriptはJavaScriptの上にある言語なので、JavaScriptの仕様や歴史と切り離して考えることはできません。普段はあまり使っていない`class`について、言語仕様としての積み重ねや難しさを知れたのが面白かったです。

## TS 7: How We Got There

https://2026.tskaigi.org/talks/37

`tsgo`の実装についてのセッションでは、TypeScriptコンパイラがGoで書き直される話について、背景や実装の流れを知ることができました。自分はそれまで「TypeScriptのコンパイラがGoになるらしい」くらいの理解でしたが、なぜその取り組みが必要なのか、今後TypeScriptの開発体験にどう影響しそうなのかを考えるきっかけになりました。

# Day2

## 400超のデータポイントを型で制す —— UPSIDERの与信審査エンジンを支えるTypeScriptの「柔軟性」と「結合力」

https://2026.tskaigi.org/talks/39

審査を毎日行うようなプロダクトで、バックエンドの技術選定としてJava、Go、TypeScriptを比較し、最終的にTypeScriptを採用したという話がありました。TypeScriptは静的型付け言語としての堅さがありつつ、JavaScript由来の柔らかさも持っているという点が選定理由として語られていました。

400以上の特徴量を扱うためにZod schemaでフラットに管理し、境界では`z.parse`や`z.partial`を使うという話も印象的でした。型定義をただ書くだけでなく、実行時の値検証と合わせて使うことで、プロダクトの複雑さを扱いやすくしているのだと感じました。

AIを使った開発フローの話もありました。PRDを作り、設計レビューは人間が行い、その後の実装をAIに任せ、最後にテストで確認するという流れです。AIに任せる部分と人間が責任を持つ部分を分けることが、今後の開発では重要になりそうだと感じました。

## React の props は値の集合ではない — UI の状態を宣言するコンポーネント設計

https://2026.tskaigi.org/talks/41

Reactコンポーネントのpropsに`data`、`isLoading`、`error`が並んでいると、本来ありえない状態を表現できてしまいます。たとえば、`isLoading`がtrueなのに`data`も存在する、`error`と`data`が同時に存在する、といった状態です。

この問題に対して、discriminated unionを使うことで、状態ごとに許されるpropsを型で表現できるという話がありました。状態をbooleanの組み合わせとして持つのではなく、「loading」「success」「error」のような意味のあるまとまりとして表現することで、コンポーネントの利用側も実装側も安全になります。

一方で、`refetching`や`refetchingError`など状態が増えていくと、単純なunionだけでは扱いにくくなります。TanStack Queryの`useSuspenseQuery`のように、loadingやerrorを上位のコンポーネントで処理する設計が参考になるという話は、型だけでなくコンポーネントの責務分割としても学びがありました。

## Auth.jsからBetter Authへの移行に見る「型とランタイム」の設計思想の変化

https://2026.tskaigi.org/talks/43

認証ライブラリのセッションでは、NextAuthからAuth.js、Better Authへの流れが紹介されていました。Auth.jsではsessionの型をユーザー側で拡張できますが、callbackで実際に値を渡していなくても型推論上は存在するように見えてしまう問題があります。一方でBetter Authは、authインスタンスのconfigを元に型を推論することで、実装と型のずれを減らしているという話でした。

ライブラリの型設計は、単に型が詳しいだけでは不十分で、実際の設定や実行時の挙動とずれないことが重要なのだと感じました。

## いつテストを書くか？―ソフトウェア開発における安心と不安について考える

https://2026.tskaigi.org/talks/63

Day2で特に心に残ったのは、変更容易性とTDDの話です。

保守性とは変更容易性であり、ソフトウェアの「ソフト」は簡単に変更できることを意味する、という話から始まりました。変更が困難になったソフトウェアは、もはやソフトではなくハード化しているという表現が印象的でした。

変更容易性には、変更できそうだと思える「予期的変更容易性」と、実際に変更している中で感じる「経験的変更容易性」があるという整理も分かりやすかったです。自分がコードを読むときに「ここは触れそう」「ここは怖い」と感じるのは、単なる気分ではなく、システム理解やテスト、設計の状態に支えられた感覚なのだと思いました。

開放閉鎖原則についても、既存の要求を満たす振る舞いが変わらないことが「閉じている」、新しい振る舞いを追加できることが「開いている」と説明されていました。そして、TDDは開放閉鎖原則を徐々に閉じていく行為だという話がありました。

テストは既存の要求と期待される振る舞いの定義であり、変更しても既存テストが壊れないなら閉じていると言えます。一方で、新しい機能のテストを書くのが大変なら、設計が開いていない可能性があります。Red、Green、Refactorの最後にリファクタリングがある理由は、実装を通じて得た学習をもとに、開放閉鎖を回復させるためだという説明がとても腑に落ちました。

「いつテストを書くべきか」という問いに対して、触るのが不安ならそれがテストを書くタイミングだ、という話も印象的でした。

学生支援制度があったからこそ、現地でセッションを聞き、スカラシップランチや懇親会で人と話し、普段の学習だけでは得られない視点を持ち帰ることができました。改めて、学生支援企業の皆様、運営の皆様、登壇者の皆様に感謝します。
